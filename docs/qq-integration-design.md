# AstraChat QQ 接入设计（v0.2.0）

- 状态：**设计定稿，待实施**
- 前置：v0.1.0 的 `qq_config` 只做配置存储，界面明确标注「仅保存配置，尚未实现真实连接」
- 本文回答四件事：**走哪条接入路线**、**官方 API 到底能做到什么**、**从参考项目借了哪些设计（以及为什么没抄代码）**、**数据与安全模型怎么定**

---

## 1. 目标与非目标

### 目标

1. 让 QQ 机器人在**群聊与私聊**里收发消息，回复由 AstraChat 本地配置的模型生成。
2. 群里**不 @ 也能看到消息**，从而支持「选择性参与」而不是「被 @ 才应答」。
3. 支持**引用解析**（知道这句话是在回谁），避免把群友之间引用第三方的对话误当成指向机器人。
4. 具备**硬边界**：白名单、黑名单、权限分层、回复内容审计、发送节流。
5. 复用 AstraChat 既有的东西：模型提供商配置、人格（系统提示词）、对话持久化。

### 非目标（v0.2.0 明确不做）

- 群管理动作（禁言、踢人、审批入群）——风险高、与「聊天客户端」定位无关。
- 表情包仓库、黑话学习、朋友圈式社交状态机——这些是「AI 仿真群友」的进阶玩法，留待后续。
- 多账号、多机器人实例。
- 富媒体**发送**（只做文本发送；富媒体**接收**要解析）。

## 2. 路线决策：官方 Bot API

### 2.1 两条路线

| | A. 官方 QQ 开放平台 Bot API | B. 第三方协议（OneBot v11 / NapCat / SnowLuma） |
|---|---|---|
| 凭据 | **AppID + AppSecret**，换 access_token | OneBot 的 accessToken（**无 AppID/AppSecret**） |
| 前置依赖 | 无，纯服务端对接 | 用户必须自行安装并扫码登录一个协议端进程 |
| 群内身份 | 官方机器人（有独立标识与昵称） | **个人号**，与真人账号同级 |
| 合规 | 腾讯官方渠道 | 违反 QQ 用户协议，账号有被封风险 |
| 稳定性 | 官方承诺的接口 | 依赖协议端与 QQ 客户端版本的对抗 |
| 进群方式 | 群主/管理员拉机器人入群 | 任何登录的号都能进 |

### 2.2 关键取证：官方 API 支持**全量群消息**

这条决定了路线选择，必须写清来源。腾讯官方文档明确写道：

> **当机器人开启了「接收所有消息」功能后，群里的每一条消息（不限于@机器人）都会推送此事件。**
> —— [群消息（全量模式）GROUP_MESSAGE_CREATE](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/group_message_create.html)

事件体（官方文档字段表）已经覆盖了我们需要的绝大部分信息：

| 字段 | 说明 | 对我们的用途 |
|---|---|---|
| `author.member_role` | `member` / `admin` / `owner` | **权限分层直接可做**，不必自己维护 owner 名单的准确性 |
| `content` | 消息文本（已去除 @ 机器人前缀） | 正文 |
| `mentions[]` | 消息中 @ 的用户列表 | 判断是否点名机器人 |
| `message_scene.ext[]` | `msg_idx` / `ref_msg_idx` / `auth_token` | **引用解析**的关键 |
| `message_type=103` + 递归 `msg_elements[]` | 引用消息 / 聊天记录（0 文本、3 卡片、101 并行、102 记录、103 引用） | 引用链、聊天记录合并转发 |
| `attachments[]` | `content_type`：`voice` / `image/jpeg` / `image/png` / `image/gif` / `video/mp4` / `file`；图片带 `width`/`height`/`size` | 多模态输入 |
| `attachments[].voice_wav_url` + `asr_refer_text` | 语音转 WAV 的 URL，以及**语音 ASR 参考文本** | 语音消息可直接用 ASR 文本，省一整套 STT |
| `ark_data` | `ark_type`：小程序 / 音乐 / 位置 / 图文卡片；`fields` 里有 `title`/`desc`/`jump_url` 等 | 卡片消息降级成可读文本 |
| `group_openid` / `author.member_openid` | 群与成员的**机器人视角唯一标识** | 白名单主键 |

**这条推翻了一个常见误解**（我最初也这么以为）：以为「想读群聊就得用第三方协议」。官方 API 在开启全量模式后就能读全量群消息。

### 2.3 消息频控与时效（官方文档）

发送侧规则必须写进设计，因为它直接约束产品形态：

| 场景 | 规则 |
|---|---|
| 被动回复（群） | **有效期 5 分钟**，针对同一条消息**最多回复 5 次** |
| 被动回复（单聊） | 有效期 60 分钟，最多回复 4 次 |
| 主动消息（群） | Bot 维度 60/qpm（认证后）或 30/qpm（未认证）；**单群 20/qpm**；**每日上限 1000 条/群** |
| 主动消息（单聊） | 单用户每日上限 1000 条；另有互动召回 `is_wakeup`（4 个周期各 1 条） |
| 撤回 | 发送后 **2 分钟内**可撤回 |
| 去重 | 相同 `msg_id` 可能重复推送，需用 `msg_seq` 去重 |

> 来源：[消息收发概述](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html)

### 2.4 结论

**走官方 Bot API。** 理由：

1. 能力足够——全量群消息 + 引用解析 + 语音 ASR + 图片附件都在，我们希望做的功能没有一个是官方 API 做不到的。
2. **凭据字段不用推翻**：v0.1.0 已有的 `appId` / `appSecret` / `token` 正好就是官方模型的凭据，选官方路线后这三个字段与服务端对接方式完全对齐（需要重构的只有白名单部分，见 §5）。
3. 不让用户多装一个第三方进程、不引入封号与协议对抗风险，符合「轻量客户端」的定位。
4. 第三方的「更深入」有很大一部分来自它是**个人号**（能自由发言、能禁言踢人），而不是来自它的代码质量——那部分深度是合规代价换来的，我们不换。

### 2.5 由此产生的**硬约束**（必须让用户知道）

1. **用户可以在 QQ 客户端关掉「允许主动发送」**，关闭后机器人的主动消息一律发送失败。→ **「AI 主动搭话」不能保证送达**，必须做成「尽力而为 + 失败不报错到用户脸上」。
2. **被动回复有窗口与次数上限**（群聊 5 分钟 / 5 次）。→ 长对话必须收敛在窗口内，不能对同一条消息反复回。
3. **白名单不能填 QQ 号/群号**。官方只给 `openid`，不给 QQ 号。这是对 v0.1.0 UI 的实质性影响，见 §5.3。

## 3. 能力映射：参考项目功能 → 官方 API 可做性

参考项目 `qq-bridge` 的功能逐条映射（这是「我们能做到多深」的对照表）：

| qq-bridge 功能 | 官方 API | 我们的做法 |
|---|---|---|
| 群消息全量接收（不 @ 也收） | ✅ `GROUP_MESSAGE_CREATE`（需开「接收所有消息」） | 订阅 Intent `GROUP_AND_C2C_EVENT` (1<<25) |
| @ 检测 | ✅ `mentions[]` / `GROUP_AT_MESSAGE_CREATE` | 直接用 |
| 权限分层（owner / 群友） | ✅ `author.member_role` + 自配 owner openid | `member_role` + `qq_contacts.policy` |
| 引用解析（谁在回谁） | ✅ `message_scene.ext[ref_msg_idx]` + `message_type=103` | 拼成 `[引用 <昵称>：<原文>]` 注入 |
| 图片多模态 | ✅ `attachments[].url`（带 `content_type`/尺寸） | 主进程下载后转 data URL 送模型 |
| 语音消息 | ✅ `voice_wav_url` + **`asr_refer_text`** | 直接用 ASR 文本，v0.2.0 不做 STT |
| 合并转发 / 聊天记录 | ✅ `message_type=102` + 递归 `msg_elements` | 展开成可读文本 |
| 卡片 / 小程序 / 音乐 | ✅ `ark_data.ark_type` + `fields` | 降级成 `[卡片 标题 描述]` |
| 引用回复发送 | ✅ 发消息接口带 `msg_id` 即被动回复 | 回复时带 `msg_id` |
| 分条 / 错落发送 | ⚠️ 受单群 20/qpm 与 5 次被动回复约束 | 节流 + 上限内分条 |
| 主动搭话（仿真群友） | ⚠️ 1000 条/群/天，但**用户可关「允许主动发送」** | 做，但必须容忍失败 |
| 表情包（sticker）收发 | ❓ 官方无 sticker 收发接口（富媒体可发图片） | 不做 |
| 戳一戳（poke） | ❓ 官方是否有对应能力**待核实** | v0.2.0 不做 |
| 群管理（禁言/踢人） | ✅ 官方有群聊管理 API | **非目标**，主动不做 |
| 回复内容审计（拦路径/凭据） | 与 QQ 无关 | ✅ 做，见 §6.4 |
| 白名单 fail-closed | 与 QQ 无关 | ✅ 做，见 §6.2 |
| 断线期间排队 | 与 QQ 无关 | ✅ 做（内存队列，**并写明保证边界**） |
| SSRF 加固的联网抓取 | 与 QQ 无关 | 若以后让群 agent 联网，按 §6.5 清单做 |
| 黑话学习（人工确认才转正） | 与 QQ 无关 | v0.2.0 不做；但「自动候选 + 人工确认」这个模式值得留给以后的记忆功能 |
| DSH 桥接、MCP server、agent preset | — | **完全不适用**：AstraChat 不接 DSH，是独立客户端 |

## 4. 借鉴边界与授权合规（重要）

### 4.1 事实

参考项目 `qq-bridge`（github.com/Derpyu520/qq-bridge，v0.1.5）：

- 仓库内**没有 `LICENSE` 文件**；
- 根 `package.json` 是 `"private": true` 且**没有 `license` 字段**；
- 唯一声明 MIT 的是其子包 `plugins/qq-mode-console/package.json`。

按默认规则，**无许可证 = 保留所有权利（all rights reserved）**，比 AGPL 更严格（AGPL 至少授予了使用许可）。

### 4.2 我们的处理

| 行为 | 允许？ | 说明 |
|---|---|---|
| 阅读其源码，理解架构与设计意图 | ✅ | 思想、方法、事实不受版权保护 |
| 把它的代码复制/改写进本仓库 | ❌ | 无授权，会让本仓库的 MIT 声明站不住 |
| 直接依赖它使用的 npm 包 | ✅ | 包自身有许可证（见下） |
| 复制其文档中的官方链接与公开事实 | ✅ | 事实与链接不属于作品表达 |

### 4.3 我们借鉴的**设计思路**清单

为可追溯，明确列出哪些设计是「受其启发、但由我们自行实现」：

1. **fail-closed 白名单**：空白名单时不响应任何消息，而不是默认全放行。
2. **权限分层**：管理命令由**程序硬执行**、不交给模型判断；群友无法通过话术越权。
3. **回复内容审计**：发送前用正则拦截本机路径与凭据特征，且**凭据关键词必须带赋值关系**才判定（避免「这个 token 真难用」被误拦）。
4. **按代理对安全的按长度切分**：切点落在 UTF-16 代理对中间时要前移一个码元，否则 emoji 会被切成乱码；并对「最大长度极小 + 开头是 emoji」做零进度死循环防护。
5. **Markdown → 纯文本**：QQ 不渲染 Markdown，链接保留 `文字 (url)` 形式。
6. **断线期间的内存排队**，并在文档里**如实写明保证边界**（进程退出会丢队列、不保证补发）。
7. **发送节流**：固定间隔 + 每分钟/每小时上限，防触发风控。
8. **单实例**：同一时间只允许一个连接实例。

以上 8 条均**不复制其代码**，由我们在 `src/services/qq/` 下自行实现并配套单测。若将来确需引用其代码，必须**先取得作者授权**并在 `ATTRIBUTION.md` 中登记。

### 4.4 可合法复用的依赖

官方 Bot API 路线下，收发消息用 WebSocket + HTTPS 即可，**无需引入任何第三方 SDK**（这也是选官方路线的一个附带好处：依赖面更小）。若后续需要，`@tencent-connect/qqbot-nodejs`（MIT）是可选的官方 SDK。

## 5. 数据模型

### 5.1 现状（v0.1.0，schema v1）

```sql
qq_config(id PK, app_id, app_secret, token, group_ids JSON, enabled, status, status_message, updated_at)
```

单例行 `id='default'`。问题：白名单用 JSON 塞在单行里，无法承载「见过但未授权」的中间态，也无法显示昵称/群名。

### 5.2 目标（schema v2）

**`qq_config`（单例）只放凭据与全局策略**：

| 列 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `app_id` / `app_secret` / `token` | TEXT | `''` | 官方凭据（沿用 v0.1.0） |
| `enabled` | INTEGER | 0 | 总开关 |
| `intents` | INTEGER | 0 | 事件订阅位掩码；全量群消息需要 `1<<25` |
| `sandbox` | INTEGER | 1 | 用沙箱环境还是正式环境 |
| `owner_open_ids` | TEXT(JSON) | `'[]'` | 管理员 openid 列表（管理命令只看这个） |
| `allow_all_when_empty` | INTEGER | **0** | **fail-closed 默认值**：0 = 白名单为空时谁都不理 |
| `reply_in_private` | INTEGER | 1 | 私聊是否应答（仍受 `qq_contacts.policy` 约束） |
| `audit_enabled` | INTEGER | 1 | 发送前内容审计开关 |
| `send_delay_ms` | INTEGER | 300 | 连续发送间隔 |
| `max_send_per_minute` | INTEGER | 8 | 每分钟发送上限 |
| `max_send_per_hour` | INTEGER | 60 | 每小时发送上限 |
| `max_reply_chars` | INTEGER | 500 | 单条回复字符上限（超出切分） |
| `status` / `status_message` / `updated_at` | — | — | 沿用 v0.1.0 |

**新增 `qq_contacts`（多行）—— 这是 v0.2.0 的关键表**：

```sql
CREATE TABLE qq_contacts (
  open_id       TEXT PRIMARY KEY,          -- group_openid 或 user_openid
  kind          TEXT NOT NULL CHECK (kind IN ('group','private')),
  display_name  TEXT,                      -- 群名 / 昵称（事件里可能有）
  policy        TEXT NOT NULL DEFAULT 'none' CHECK (policy IN ('none','allow','deny')),
  first_seen_at INTEGER NOT NULL,
  last_seen_at  INTEGER NOT NULL,
  message_count INTEGER NOT NULL DEFAULT 0
);
```

`policy='none'` 表示「见过但未授权」——机器人必须**先收到过消息**才知道 openid，所以这张表同时承担了「待授权列表」的角色。

### 5.3 迁移 v1 → v2

1. `ALTER TABLE qq_config` 增加上表新列，默认值按 5.2。
2. 建 `qq_contacts`。
3. **把老的 `group_ids` 数组迁移成 `qq_contacts` 行**（`kind='group'`、`policy='allow'`、`display_name` 留空、时间戳取迁移时刻），以保留用户已有的白名单意图。
4. `DROP COLUMN group_ids`（SQLite ≥ 3.35 支持；本项目 better-sqlite3 13 带 SQLite 3.53）。
5. `PRAGMA user_version = 2`。

迁移必须**幂等且可重入**：v1 数据迁完再跑一次不应重复插入。

### 5.4 对 UI 的实质影响：白名单不能再手填数字

v0.1.0 的设置页让用户填「群号」（纯数字校验）。官方 API **只给 openid，不给 QQ 号**，用户无从手填。

**新 UX**：

1. 用户只填 AppID / AppSecret / Token，先连接。
2. 机器人在**观察模式**（未授权也记录）下把收到的来源写进 `qq_contacts`。
3. 设置页展示「见过的群 / 私聊」列表（带昵称与消息数），用户逐个设为**允许 / 拒绝 / 忽略**。
4. 只有 `policy='allow'` 的来源，消息才会投给模型。

这比手填数字更安全（不会填错）也更省事（不用去查群号）。原有「群号」输入框改为「已发现的来源」列表。

## 6. 安全模型

### 6.1 威胁模型

| 威胁 | 后果 | 对策 |
|---|---|---|
| 陌生群友诱导模型泄露本机信息 | 路径、密钥外泄 | 回复审计（§6.4）+ 工具面最小化 |
| 模型把 API Key 复述到群里 | 凭据泄露 | 审计拦截 + 提示词禁止 + **Key 永不明文进 prompt** |
| 群友伪造成管理员下命令 | 越权改人格/模式 | 管理命令由程序按 `owner_open_ids` **硬校验**，不看模型判断 |
| 机器人被拉进不该进的群乱说话 | 骚扰 / 封号 | fail-closed 白名单 |
| 发送过快触发风控 | 功能受限 | 节流（§6.6） |
| 恶意消息撑爆上下文 | 成本 / 崩溃 | 单条与总长度上限、消息数上限 |

### 6.2 白名单：fail-closed

- `qq_contacts.policy` 三态：`allow` / `deny` / `none`。
- **deny 优先于 allow**。
- `policy='none'` 且 `allow_all_when_empty=0`（默认）→ **不投递给模型**，只记入 `qq_contacts` 供用户授权。
- 只有把 `allow_all_when_empty` 显式打开才可能放行未知来源；UI 上必须用警示文案说明「等于把账号交给模型」。

### 6.3 权限分层

| 主体 | 判定依据 | 权限 |
|---|---|---|
| 管理员 | `open_id ∈ owner_open_ids`，或事件里 `member_role ∈ {admin, owner}`（可开关） | 正常对话 + `/` 管理命令（`/role`、`/silent`、`/status`、`/reset`） |
| 群友 | 其他已授权来源 | **仅正常对话**；`/` 命令与静默指令被程序拦截，不进入模型 |

管理命令**在桥接层直接执行**，不产生模型调用——这样话术诱导在设计上就不可能生效。

### 6.4 回复审计（发送前拦截）✅ 已实现

发送前对文本做一次检查，命中即**整条不发送**并记录（而不是脱敏后发出，避免半句话造成误解）：

- **本机路径**：`C:\...`、`\\host\share`、`/home/`、`/Users/`、`/etc/`、`/var/`、`/root/`
- **凭据特征**：`token` / `密码` / `密钥` / `password` / `secret` / `api_key` / `authorization` / `bearer` / `access_key` / `credential`，**且必须带赋值关系**才判定。

实现于 [`src/services/qq/audit.ts`](../src/services/qq/audit.ts)，纯函数、与 QQ 连接解耦，
47 个单测见 [`tests/qq-audit.spec.ts`](../tests/qq-audit.spec.ts)。

#### 实施时相对本节初稿的三处加强

1. **多了一层「精确匹配已知密钥」**（这是最强的一层）。初稿只有启发式规则，但威胁模型里
   最要命的一条是「模型把我们自己的 API Key 复述出去」——对这种场景，把**已知密钥原文**
   传给审计函数做精确匹配，零猜测、零误报，比任何正则都可靠。
   长度 < 8 的条目会被忽略（否则几乎任何文本都会命中）。

2. **把「赋值关系」拆成了三档**，因为初稿那句话不够细，直接实现会误伤：

   | 分隔符 | 右侧要求 | 理由 |
   |---|---|---|
   | `:` `=` `：` | 任意非空白串（≥3 字符） | 显式赋值本身就是技术写法；允许中文值是因为**中文口令也是口令** |
   | `是` `为` | 必须像技术串 | 中文系词太常见，「你的 token 是怎么生成的」必须放过 |
   | 纯空白 | 必须像技术串（≥8 字符） | 「token 真难用」与「token abc12345def」的区别就在这 |

   「像技术串」= `[A-Za-z0-9_\-./+=]`，中文字符天然不满足，因此中文句子不会误报。
   负例（必须放过的句子）占了测试的一半：`这个 token 怎么申请？`、`请把 password 字段留空`、
   `Bearer 令牌需要先配置`、`密码学是一门学科`、`我 12:30 到`、
   `见 https://example.com/Users/guide`。

3. **审计结果本身不存秘密**。`AuditFinding` 只给**规则名 + 位置 + 脱敏预览**
   （`sk…（共 17 字符）`），不保留命中原文——否则「把密钥写进日志」等于换个地方泄露。
   要记录被拦的回复时用 `redactForLog()`，它把敏感片段替换成 `[已拦截:<规则>]`。

#### 已知的误报边界（有意接受）

- **通用 Unix 路径**会被拦：模型解释 `/etc/nginx/nginx.conf` 这种文档性路径也会命中。
  代价是「偶尔不说话」，而漏掉的代价是「泄露本机目录结构」，不对称，故选保守。
- **显式冒号后的中文值**会被拦：`token：这个不好用` 这种写法会误伤。但放宽它就抓不到
  中文口令（`密码：我的生日是1990`），取舍后选择抓。
- **占位符**会被拦：`API_KEY=your_key_here` 也命中。它长得就是赋值，拦下无害。

以上都可通过 `AuditOptions` 的 `checkPaths` / `checkCredentials` 单独关闭。

### 6.5 若引入联网能力（预留，v0.2.0 不做）

清单照抄参考项目的加固维度（自行实现）：仅 http/https；拒绝 localhost / 私有网段 / 链路本地 / CGNAT / 带凭据 URL；**DNS 解析结果全量校验**；**每一跳重定向都重新校验**；响应体限量读取。

### 6.6 发送节流

- 每条之间 `send_delay_ms`（默认 300ms）。
- 每分钟 `max_send_per_minute`（默认 8）、每小时 `max_send_per_hour`（默认 60）。
- 超出 → 排队或丢弃并在日志与状态里体现，**不静默丢**。
- 被动回复遵守「同一条消息最多 5 次 / 5 分钟窗口」。

## 7. 消息管线

### 7.1 入站

```
QQ WebSocket 事件
  → 去重（msg_id + msg_seq）
  → 解析：正文 / @列表 / 引用(ref_msg_idx, 103) / 附件(图片, 语音ASR) / 卡片(ark_data)
  → 来源识别：group_openid / user_openid → upsert qq_contacts
  → 授权判定：policy + 黑名单 + allow_all_when_empty   ← 不通过则只记录
  → 权限判定：是否管理员（决定是否先跑 / 命令）
  → 组装 prompt：人格系统提示词 + 引用上下文 + 附件
  → 走既有流式管线（复用 electron/chat.ts 的模型调用）
  → 生成回复
```

**复用点**：模型调用与流式解析完全复用 v0.1.0 已实现并测过的 `src/services/openai.ts` + `electron/chat.ts`，QQ 只是另一个「输入源 / 输出目标」。

### 7.2 出站

```
模型回复（Markdown）
  → Markdown → QQ 纯文本                （C 阶段模块）
  → 回复审计：命中则不发送并记录          （§6.4）
  → 按长度上限切分（代理对安全）          （C 阶段模块）
  → 节流队列
  → 发送（被动回复带 msg_id；主动消息容忍失败）
  → 写 qq_activity 日志（用于设置页展示与排查）
```

### 7.3 连接与容错

- 主进程持有唯一连接实例（单实例）；渲染进程只通过 IPC 读写配置与查看状态/日志。
- WebSocket 断线**指数退避重连**；断线期间入站消息进内存队列（每来源上限 50 条，满则丢最旧）。
- **保证边界必须写进 UI 与文档**：进程退出会丢队列；断线期间已生成的回复不保证补发。
- 凭据（AppSecret/Token）沿用 v0.1.0 的掩码展示策略，**不进渲染进程的日志**；模型 prompt 里永不出现凭据。

## 9. 未决问题

1. **戳一戳（poke）官方是否支持** —— 待核实，v0.2.0 不做，不影响其他设计。
2. **`GROUP_MESSAGE_CREATE` 的「接收所有消息」开关在开放平台后台的具体位置与审核要求** —— 需要真实账号确认；若该开关需要申请/审核，需要在 UI 里给出指引。
3. **`display_name` 从哪来** —— 群消息事件里有 `author.username`，但**群名**可能需要额外调用群信息接口；若无接口则列表里用「群 <openid 前 8 位>」占位。
4. **管理命令集合** —— `/role`、`/silent`、`/status`、`/reset` 是否够用；要不要 `/model` 切模型。
5. **私聊默认策略** —— 是默认需授权（更安全）还是默认应答（更好用）。当前设计倾向需授权。
